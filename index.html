The problem

Hospitals want to train diagnostic models on each other's data, but HIPAA, GDPR and India's DPDP Act make pooling patient records difficult. No single hospital has enough variety in patients, scanners and disease prevalence to train a robust model alone.

Federated learning (FL) is the common answer: each hospital trains locally and shares only model updates. The paper's central claim is that data locality is necessary but not sufficient for security. The aggregator has to trust that every update comes from honest training, and in a clinical setting a poisoned classifier can influence a real diagnosis.

FL also does not make a system compliant with these laws by itself. Each framework asks for more than keeping data on-site.

What the paper contributes

  • A survey of four attack classes against federated medical imaging.
  • A review of five defense families and the trade-offs between them.
  • An experiment on real chest X-rays measuring what one malicious hospital can do, and how well three Byzantine-robust rules recover.

How federated learning works

Training runs in rounds (FedAvg). The server sends the current global model to the hospitals. Each hospital trains it on its own images and returns the result. The server then averages the returned models, weighting each by the number of training examples it reports:

The server never sees patient-level data. It also cannot check that an update came from honest training, and the dataset size is self-reported. That gap is the attack surface.

Why hospitals make this harder

Hospital data is non-IID: disease prevalence, demographics and imaging hardware all differ. An honest hospital can therefore look statistically unusual for legitimate reasons. Many robust aggregation rules work by down-weighting updates that look unusual, so they risk treating an atypical hospital as an attacker. The paper calls telling heterogeneity from attack the central open problem for robust FL in clinics.

Defenses

No defense covers every threat, and each one costs something in privacy, robustness, accuracy or computation.

Defenses reviewed in the paper
DefenseWhat it doesWhat it costs
Secure aggregationMasks updates cryptographically so the server only sees the sum.The server cannot inspect single updates, so it cannot run anomaly detection.
Differential privacyClips contributions and adds noise to limit what any record or client reveals.Accuracy falls as the privacy budget tightens.
KrumPicks the single update closest to its nearest neighbors and discards the rest.Throws away honest information each round; pairwise distances scale as O(n²).
Trimmed mean and medianWork per coordinate, dropping extremes (trimmed mean) or taking the middle value (median).Need an assumed bound on malicious clients; median discards more usable signal.
FLTrustWeights updates by similarity to one computed on a small trusted dataset.Needs a trusted dataset that represents a very varied federation.
FLDetectorTracks each client across rounds and flags inconsistent behavior.Needs update history, which secure aggregation hides.
Participant authenticationVets which institutions may join, guarding against Sybil attacks.Does not stop a vetted participant from misbehaving.

The experiment

Data
Chest X-Ray Images (Pneumonia): 5,863 pediatric radiographs, normal or pneumonia, resized to 48 × 48.
Federation
Five hospitals with disjoint data and pneumonia prevalence from 30% to 70%.
Model
A small CNN with 75,041 parameters, trained for 15 federated rounds with a fixed seed.
Attack
One hospital flips its labels and multiplies its update by 8, raising its influence from about 21% to about 68%.
Compared
FedAvg with and without the attack, then the attack against Krum, trimmed mean and median.

The authors also report two bugs they caught: an all-zero weight initialization that silently froze training, and a sampling step that let hospitals share identical images. Both produced believable but wrong results without any error.

Results

Convergence and cost

  • Poisoned FedAvg collapsed immediately, by round 2, instead of degrading gradually.
  • Trimmed mean and median settled by round 3. Krum took until about round 7.
  • All three robust rules ran in about 1.7 to 1.8 seconds per run at n = 5. Krum's cost grows quadratically with the number of hospitals.

Takeaways

  1. Federating is not securing. A single bad participant can reduce the model to chance.
  2. Robust rules are not interchangeable. Under the same attack and data, accuracy ranged from 75.0% to 83.0%, so the specific rule matters.
  3. Match the defense to the threat model. Secure aggregation, anomaly detection and robust aggregation pull against each other.
  4. Validate on non-IID clinical data. Theoretical guarantees alone are not a substitute.

Limitations

The federation is small (five hospitals) and the model is small. Only one attack was tested, one malicious hospital using label flipping with 8× scaling, on one binary task. Combinations of defenses, such as differential privacy on top of a robust rule, were not evaluated. The authors caution against generalizing beyond this configuration.
